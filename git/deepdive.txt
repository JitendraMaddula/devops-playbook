What is Version Control?
    Version Control is a system that tracks changes made to files over time. It helps developers collaborate, maintain history, and restore previous versions if needed.
Distributed Version Control System vs Centralized Version Control System
    Centralized (CVCS): Relies on a single central server to store the project history. Developers only download a snapshot of the latest files
        Requires internet to commit or view history. If the server dies, work stops.
        Examples: Subversion (SVN), Perforce.
    Distributed (DVCS): Every developer downloads a complete copy of the entire project and its full history to their local machine.
        Works offline. You can commit, branch, and view history without the internet. Every local copy is a full backup.
        Examples: Git, Mercurial.

Create Repo
    git init --> Initialize a new Git repository locally. This creates a .git directory in your project folder, which contains all the necessary metadata for the repository.

Clone Existing Repository
    git clone <repository_url> --> Clone a remote repository from GitHub to the local machine. This command creates a copy of the remote repository on your local machine.

Check Repository Status
git status -->Check if the repository is initialized and track changes in files/folders. This command also shows the status of the working directory and the staging area.

HEAD Concept
HEAD: A pointer to the latest commit in the current branch. It represents the most recent commit on the current branch and serves as a reference point for various Git operations.

Stage changes
git add <filename> --> Add changes from the working directory to the staging area. This marks the changes as ready to be committed.
git add .          --> Stages all new and modified files.

Commit Changes
git commit -m "<message>" -->Commit staged changes to the local repository with a descriptive message. The -m flag allows you to include a commit message describing the changes.

View Commit History
git log -->Display a log of all commits in the current branch. It shows the commit hash, author, date, and commit message.
git log --oneline -->Display a concise log of commits, showing only the commit hash and message.

git commit --amend -m "new commit message" --> update commit message of recent commit

Merge Branches
git merge <branch_name> -->Merge changes from a specified branch into the current branch.

Merge Conflict
    A merge conflict occurs when Git cannot automatically figure out which changes to keep when combining two branches. The most common reasons are:
        •	Same-line edits: Two branches modify the exact same line(s) in the same file differently.
        •	Modify vs. Delete: One branch updates a file, while the other branch completely deletes that same file.
        •	File creation collision: Both branches create a new file with the exact same name but different content.
    Resolve the conflict manually, then:
        git add .
        git commit

Rebase
git rebase <branch_name>: Apply changes of the current branch on top of another branch. This can lead to a cleaner commit history compared to git merge.

Reset
Moves the branch pointer to a previous commit.
    Soft Reset
        git reset --soft HEAD~1
        Removes the last commit but keeps changes staged.
    Mixed Reset
        git reset HEAD~1
        Removes the last commit and un-stages changes.
    Hard Reset
        git reset --hard HEAD~1
        Deletes the last commit and all associated changes.

Revert
Safely undoes a commit by creating a new commit.
git revert <commit_id>

Restore
to get deleted file back
git restore file.txt

Key difference between restore, reset, revert
    git restore works in working directory and staging
    git reset works in all 3 and also rewrites history
    git revert works in all 3 without rewriting history but adds a new commit

Bare repository is a Git repository that does not have a working directory.
In a standard Git repository, you have your actual project files (the code you can open, edit, and run) plus a hidden .git folder that tracks all the version history. 
A bare repository contains only the version control data (the contents normally found inside the .git folder) and no editable project files.

Git hooks are custom scripts that Git automatically runs before or after key events, such as committing, pushing, or merging code. 
They act as automated trigger points, allowing you to enforce rules, run tests, or automate tasks in your development workflow.
location --> .git/hooks

types of githooks
    Git hooks are custom scripts triggered by specific actions in a Git repository. They are divided into two main categories:
•	Client-Side Hooks: Run on your local machine.
•	Workflow hooks: pre-commit, prepare-commit-msg, commit-msg, post-commit.
•	Other hooks: pre-rebase, pre-push, post-checkout, post-merge.
•	Server-Side Hooks: Run on the remote repository when receiving pushes.
•	pre-receive, update, post-receive.

What are Branch protection rules --> Branch protection rules are administrative features provided by Git hosting platforms to enforce specific workflows and safeguard important branches.
•	Requiring pull requests/merge requests before code can be merged.
•	Requiring a specific number of approvals from other developers.
•	Forcing status checks (like CI/CD pipeline tests) to pass before merging.
•	Preventing anyone (even admins) from force-pushing (rewriting history) or accidentally deleting the branch.

Difference between git reflog and git log
    git log is the official biography of your project. It shows the public, permanent history of the code.
    git reflog is your private, local journal. It records absolutely everything you did on your specific machine, including the mistakes, the erased history, and the dead ends.

Real time use case of githooks with reference to opt pipelines
A primary real-world use case for Git hooks is protecting our CI/CD pipelines by 'shifting left.' We configure local pre-commit hooks on the developers' machines to run fast, lightweight checks—such as scanning for hardcoded secrets or formatting errors—before a commit is even allowed. By blocking bad code locally, we prevent it from ever reaching the repository, which stops our main Jenkins pipelines from wasting compute time and money on builds that are guaranteed to fail."

Branching stretegy:
Trunk-Based Development (TBD)In Trunk-Based Development, all developers merge their changes into a single central branch—usually called main or trunk—frequently throughout the day.
    How it works: Developers pull from main, make small changes locally or in short-lived feature branches, and merge back immediately. Incomplete features are hidden using feature flags (or feature toggles) so the code can sit safely in production without breaking user experiences.
GitHub flow: GitHub Flow is a lightweight, agile, and branch-focused workflow designed around regular deployments
    How it works: The main branch is always stable and ready to deploy. When a developer wants to add a feature or fix a bug, they create a descriptive branch off of main. They push their commits to this branch, open a Pull Request (PR) for review, test the changes, and finally merge the branch back into main.
Git flow: GitFlow is a strict, highly structured branching model that dictates distinct roles for different branches. It isolates development from production preparation.
    How it works: It relies on two long-lived branches: master (production) and develop (pre-production integration). Supporting branches include short-lived feature/* branches (built off develop), release/* branches (forked from develop for final testing and merged into both master and develop), and hotfix/* branches (forked from master to address emergency production bugs).
