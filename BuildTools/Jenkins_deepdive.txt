What is Continuous integration, continous delivery and continous deployment
•	Continuous Integration (CI): It is the automated process of frequently merging developers' code updates into a shared project and instantly testing them to catch bugs early.
•	Continuous Delivery (CD): It is the practice of ensuring that every tested code change is safely packaged and always ready to be released to users with the manual click of a button.
•	Continuous Deployment (CD): It is the fully automated process where every code change that passes testing is immediately released directly to the users without any human intervention.

What are plugins
Plugins in Jenkins are add-on software modules that you install to give Jenkins new features and allow it to communicate with other tools.

Important plugins of jenkins
•	Pipeline: The most critical plugin. It allows you to write your build processes as code (using a Jenkinsfile) rather than configuring them manually in the UI.
•	Git Plugin: Essential for connecting Jenkins to your Git repositories (GitHub, GitLab, etc.) to pull code and trigger builds automatically.
•	Credentials Binding: Crucial for security. It allows you to inject secrets (like API tokens, passwords, and SSH keys) into your builds without exposing them in your code or logs.
•	Blue Ocean: Upgrades the classic Jenkins interface to a modern, visual dashboard, making it much easier to monitor pipelines and troubleshoot failed builds.
•	Docker Pipeline / Kubernetes: These plugins are standard for modern infrastructure, allowing you to run your build jobs inside clean, isolated containers that spin up and down as needed.
•	Role-Based Access Control (RBAC): Important for teams, this allows you to define specific permissions (view, build, configure) for different users or groups.

Keeping Background Processes Alive After Build:
   To run an application or script and keep it running after the Jenkins build is completed, you must bypass the Jenkins Process Tree Killer.
   Method: Set the environment variable `BUILD_ID=dontKillMe` (or `JENKINS_NODE_COOKIE=dontKillMe` in newer Jenkins versions) before your command.
   Example: `daemonize -E BUILD_ID=dontKillMe /path/to/command` or simply exporting the variable before executing a background script.

A hotfix is an urgent, rapidly deployed code update designed to fix a specific, critical bug or security vulnerability in a live production environment.
A software patch is a planned, routine update that bundles multiple bug fixes, security enhancements, and minor improvements into a single release.

What is waterfall and agile methodology
   •	Waterfall is a linear and sequential approach. You complete the project in strict phases (plan, build, test, deploy), finishing one phase completely before starting the next. It is rigid and delivers the final product all at once at the very end.
   •	Agile is an iterative and flexible approach. You break the project down into short cycles (sprints), delivering small, working pieces of the product continuously. It embraces changing requirements and constant customer feedback.

Difference between monolithic app and micro service app
   •	Monolithic Architecture is a traditional approach where the entire application is built as a single, tightly coupled codebase. All features are deployed together, meaning if you need to update or scale one feature, you have to redeploy and scale the entire application.
   •	Microservices Architecture breaks the application down into small, independent services (e.g., login, payment, cart) that communicate via APIs. Because they are loosely coupled, you can update, deploy, and scale each service individually without affecting the rest of the application.

Jenkins Build Triggers
   Trigger builds remotely - Allows you to trigger a build by sending an HTTP request to a specific Jenkins URL with an authentication token, enabling external scripts, tools, or third-party applications to start jobs on demand.
   Build after other proiects are built - Automatically starts a build as soon as a specified "upstream" project finishes running, linking jobs together to create sequential pipelines or dependent workflows (e.g., deploying only after the testing job succeeds).
   Build periodically - Schedule builds to run at specific times using cron-like syntax, regardless of code changes.
   GitHub hook trigger for GITScm polling - GitHub sends a notification to Jenkins immediately when code is pushed, triggering an instant build.
   Poll SCM - Jenkins periodically checks your source control system for changes and builds only when changes are detected.

How to Set Up a GitHub Hook Trigger for Jenkins:
   1. Go to your GitHub repository settings.
   2. Navigate to "Webhooks" and click to add a new webhook.
   3. In the "Payload URL" field, enter your Jenkins URL followed by `/github-webhook/`.
   Example: http://0.0.0.0:8080/github-webhook/
   4. Click "Add webhook" and save your changes.

Logic behind web hooks of GitHub and jenkins
    When you configure a webhook in GitHub and link it to a Jenkins pipeline, the following sequence of logical steps occurs:
	1.	The Triggering Event: A developer performs an action in GitHub. This is usually a git push to a repository, but it can also be the creation of a Pull Request, a merged branch, or a new release tag.
	2.	The Payload Generation: GitHub packages all the details about that event into a JSON file (the payload). This includes the repository name, the specific branch updated, the commit ID, the commit message, and the user who made the change.
	3.	The HTTP POST Request: GitHub acts as a client and sends an HTTP POST request containing that JSON payload to a specific URL hosted by your Jenkins server (e.g., [https://your-jenkins-server.com/github-webhook/]).
	4.	The Jenkins Reception: The Jenkins server is listening on that URL. It catches the POST request and reads the JSON payload.
	5.	The Matching Logic: Jenkins scans its internal database of jobs/pipelines. It looks for any job that is configured to build the specific GitHub repository and branch mentioned in the payload.
	6.	The Execution: Once a match is found, Jenkins automatically triggers the pipeline to run (compiling code, running tests, deploying, etc.).
	7.	The Feedback Loop (Optional but common): After the build finishes, Jenkins can use the GitHub API to send a status check back to GitHub, displaying a green checkmark (Success) or a red cross (Failure) directly on the GitHub commit or Pull Request.

Security Concepts in Jenkins:
   1. Authentication
      Authentication is the process of verifying a user's identity. This can be handled through a standard login, an external LDAP (Lightweight Directory Access Protocol) server, or the internal Jenkins Database (JENKINS DB).
      * Simple Definition: Authentication answers the question, "Who are you?" It is like checking your ID badge at the door. LDAP is a central directory system companies use so you can log in with your normal work credentials, while Jenkins DB means your account is stored directly inside Jenkins.

   2. Authorization
      Authorization deals with granting permissions to users after they have successfully authenticated. It determines what specific actions a user is allowed to perform.
      * Simple Definition: Authorization answers the question, "What are you allowed to do?" It is like having a keycard that only unlocks specific rooms inside the building.

      Authorization Methods for Permissions:
         * Matrix-based: This method uses a global grid (or matrix) to assign specific permissions (like read, write, or build) to users or groups across the entire system.
         * Project-based: This allows you to grant permissions on a per-project basis. For example, a user might be able to edit and build "Project A," but they can only view "Project B."
         * RBAC (Role-Based Access Control): This method involves creating specific "roles" (such as Admin, Developer, or Tester) that have predefined permissions. You then assign users to those roles instead of managing permissions one-by-one.

How to securely store credentials in Jenkins?
   To securely store credentials in Jenkins, you store them centrally using the Credentials Plugin, which encrypts them on the Jenkins master node. To safely use them in a job, you use the Credentials Binding Plugin to inject them as temporary environment variables, which automatically masks the values in the console logs to prevent exposure. 

Types of credentials manager in jenkins
   •	Secret text: A single sensitive string, like a GitHub API token or a webhook URL.
   •	Username with password: A standard login pair, typically used to authenticate with Docker Hub, Nexus, or Artifactory.
   •	Secret file: A sensitive file that Jenkins temporarily places in the workspace during a build, like a kubeconfig file or a .env file.
   •	SSH Username with private key: Used for secure connections, like cloning a private Git repository or SSH-ing into a remote server.
   •	Certificate: Used for securely storing PKCS#12 or JKS certificate files.

Difference between Agile methodology and Devops methodology
   Agile and DevOps solve two different problems in the software lifecycle. Agile focuses on the development phase; it bridges the gap between the business and the developers through iterative sprints to ensure we are building the right product. DevOps focuses on the delivery phase; it bridges the gap between developers and operations by using automation and CI/CD pipelines to ensure that the code Agile teams write can be deployed to production instantly, safely, and reliably.

What are upstream and downstream jobs
An upstream job is the first task in a chain that triggers the next step when it finishes successfully. A downstream job is that next step, which waits for the upstream job to finish before starting its own work.

Prioritise jobs on server
By default, Jenkins runs jobs in the exact order they are triggered (first-come, first-served). To change this, I would install the Priority Sorter Plugin. This plugin lets me assign a priority number to important jobs—like a production deployment—so they jump to the front of the queue and run first.

There are four teams in your organisation. How to priorize the builds of each team? so the jobs of team x will always run before team y for example.
	1.	Organize the Jobs: First, I would organize the jobs so Jenkins can tell which team they belong to. The best way is to create separate Jenkins Folders for each of the four teams (e.g., a "Team X" folder and a "Team Y" folder).
	2.	Create Job Groups: In the global Jenkins settings, the Priority Sorter Plugin allows you to create "Job Groups." I would create a group for each team's folder.
	3.	Assign Priority Numbers: Finally, I would assign a priority number to each group. The rule is that lower numbers equal higher priority.
•	Team X gets Priority 1 (Highest)
•	Team Y gets Priority 2
•	Team Z gets Priority 3
•	Team W gets Priority 4 (Lowest)
The Result: If the server is busy, and jobs from both Team X and Team Y enter the queue, the plugin will recognize the folders and always push Team X's jobs to the front of the line so they run first.

use of throttle build plugin
The Throttle plugin puts a strict speed limit on your Jenkins server. It restricts the maximum number of jobs that are allowed to run at the exact same time. You can set this limit for a single job or a group of jobs.

Deployment types:
1. Rolling Deployment-> In a Rolling Deployment, the application instances are upgraded incrementally in small batches rather than all at once.
    How it works: The deployment system takes a subset of servers or pods offline, updates them with the new software version, verifies their health, and returns them to service. This process repeats sequentially until the entire fleet runs the new code.
2. Blue-Green Deployment -> A Blue-Green Deployment is an environment-switching strategy that eliminates risk by running two identical production environments.
    How it works: One environment (Blue) hosts the live production traffic. The new version is deployed and thoroughly tested in the idle environment (Green). Once the new version passes all health checks, a load balancer or routing layer switches all traffic instantly from Blue to Green.
3. Canary Deployment-> A Canary Deployment exposes a small, controlled percentage of live users to the new software version before rolling it out to the entire infrastructure.
    How it works: The new version is deployed to a tiny fraction of infrastructure (e.g., 5% of servers). The routing layer sends 5% of live traffic to this "canary" group. DevOps teams monitor error logs, latency, and system performance. If the metrics look good, the traffic allocation is progressively increased to 100%.
4. A/B Testing (Dark Launching) -> While often confused with Canary, A/B Testing is a business-centric deployment type focused on testing feature performance or user behavior rather than infrastructure stability.
    How it works: The new feature code is deployed to production but kept hidden behind feature flags. Based on specific user demographics, geolocations, or cookie tracking, specific user segments are routed to the new feature while the rest see the old version.
5. Recreate Deployment (All-At-Once)-> The Recreate Deployment is a legacy approach where the existing application is entirely shut down before the new version is brought online.
    How it works: All active server instances running version 1.0 are terminated simultaneously. Once the infrastructure is cleared, the system boots up version 2.0. Users experience an explicit maintenance window during the transition.
