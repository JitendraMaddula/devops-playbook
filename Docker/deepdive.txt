Docker is a software platform for building applications based on containers 

Containers & Virtual Machines:
Virtual Machines:
One solution to this problem has been virtual machines, which keep applications on the same hardware entirely separate, and reduce conflicts among software components and competition for hardware resources to a minimum. 
But virtual machines are bulky each requires its own OS, so is typically gigabytes in size and difficult to maintain and upgrade.
Containers:
Containers, by contrast, share the same underlying kernel and isolate applications execution environments from one another. Due to this they are usually in megabytes and boot up instantly.
A container is a standalone unit of software that packages together applications with all its 
dependencies and configurations.

Docker Architecture:
Docker daemon: It is also referred to as ‘dockerd’ and it accepts Docker API requests and manages Docker objects such as images, containers, networks, and volumes. It can also communicate with other daemons to manage Docker services.
    Note: A daemon is a service process that runs in the background and functionality to other processes.
Docker Client: It is the way that enables users to interact with Docker. It sends the docker commands to docker daemon. The Docker client can communicate with more than one daemon.
Docker Registry: It hosts the Docker images and is used to pull and push the docker images from registry. Docker Hub is the public registry that anyone can use, and Docker is configured to look for images on Docker Hub by default.
Docker Host: It is the physical host on which Docker Daemon is running 
and docker images and containers are created.

Docker Images:
Docker is used to create, run and deploy applications in containers. It contains application code, libraries, tools, dependencies and other files needed to make an application run.
    In simple words a Docker image is an executable file, that creates a Docker container. 
    A Docker image is comparable to an AMI in AWS.
Docker images are a reusable and can be deployed on any host. Developers can take the Docker image from one project and use them in another. This saves the user time, because they do not have to recreate an image from scratch.

Docker Image Repository:
Docker images can be stored in private or public repositories, such as Docker Hub, Amazon Container Registry etc.

Dockerfile:
it is a plane text file, that contains a set of instructions used to create a custom docker image, Default file name is Dockerfile
Default Name: Dockerfile
Commands:
docker build -t <image>:<tag> . --> To build a custom docker image using Dockerfile
docker build -t <image>:<tag> -f <dockerfile-path> . --> To build a custom docker image with a different Dockerfile name or path
docker build -t <image>:<tag> <context-path> --> To build a custom docker image with custom context path [Where docker build commands are executed]

Dockerfile Instructions:
1. FROM
this instruction is used to set the base image for the docker file. It acts as a starting point for every other instruction. A vaild docker file must always start with a From instruction.
The From instruction can appear multiple times in the Dockerfile making it a multi-stage build process.
Syntax:
FROM <image>:<tag>

2. RUN
This instruction is used to execute commands during the image build process. Useful in installing packages, creating directories, compiling code etc.
Every RUN instruction creates a new intermediate image layer but too many layers makes the image inefficient.
Syntax:
RUN <command>

3. COPY
This instruction is used to copy the files or directories from the host machine to the image.
Syntax:
COPY <host-machine-path> <image-path>
COPY --chown=<user>:<group> <host-machine-path> <image-path>

4. ADD
This instruction is also used to copy files and directories, however, the add instruction does two extra things, 
    1. auto extract tar archives to the destination, 
    2. can download files from an URL.
Syntax:
ADD <host-machine-path> <image-path>
ADD --chown=<user>:<group> <host-machine-path> <image-path>
ADD <url> <image-path>
ADD <tar-archive> <image-path>

5. CMD
this instruction is used to seta default entry point of the container. If a docker file has multiple CMD instructions only the last ones gets executed
# Syntax:
CMD <command>

6. ENTRYPOINT
This instruction is also used to set the default execution point just like CMD if multiple ENTRYPOINT are defined in Dockerfile only the last one gets executed. 
# Syntax:
ENTRYPOINT <command>
# To override the entrypoint during docker run:
docker run --entrypoint <command> <image> 

Difference B/W CMD and ENTRYPOINT:
While both the instructions are used to set a default entry point of the container in case of CMD if a command is passed during docker run the original CMD instruction set in the docker file get completely replaced. But with ENTRYPOINT if a command is passed during docker run that command will be taken as an orgument to the original ENTRYPOINT.

7. ENV
Sets environment variables that persist during the remainder of the image build process and inside the final running container.
# Syntax:
ENV <KEY>=<VALUE>
# Set env vars during docker run:
docker run --env <key>=<value> --env <key>=<value> <image>
# Set env vars using an environment file:
docker run --env-file <file-path> <image>

8. ARG
This instruction is used to set variables in dockerfiles whose value can be passed during docker build process.
# Syntax:
ARG <variable>
# (or)
ARG <variable>=<default-value>
# Passing value during docker build:
docker build --build-arg VERSION=24.04 -t <image>:<tag> .

9. WORKDIR
Sets the current working directory for any subsequent RUN, CMD, ENTRYPOINT, COPY, and ADD instructions. If the specified directory does not exist, Docker will create it automatically.
Syntax:
WORKDIR /path/to/directory

10. EXPOSE
Informs Docker that the container listens on specific network ports at runtime. This acts as documentation between the person who builds the image and the person who runs the container; it does not actually publish the port to the host machine (which requires the -p flag when running).
Syntax:
EXPOSE <port> [<port>/<protocol>...]

11. USER
Sets the username (or UID) and optionally the user group (or GID) to use for the remainder of the build process and as the default user when the container runs. This is commonly used to drop root privileges for security.
Syntax:
USER <user>[:<group>]
# or
USER <UID>[:<GID>]

12. VOLUME
Creates a mount point and marks it as holding externally mounted volumes from the native host or other containers. It prevents data stored in that directory from being committed to the container's image layer.
Syntax:
VOLUME ["/path/to/directory"]
# or
VOLUME /path/to/directory

13. SHELL
Overrides the default shell used for the shell form of commands (like RUN, CMD, and ENTRYPOINT). The default on Linux is ["/bin/sh", "-c"] and on Windows is ["cmd", "/S", "/C"].
Syntax:
SHELL ["executable", "parameters"]
(Example: SHELL ["powershell", "-command"])

Volumes:
In Docker, containers are ephemeral [Short Lived], which means any data written inside a container is lost when the container is removed. To solve this problem, Docker provides volumes and mounts to persist data even after container lifecycle.

1. Docker Volumes:
Docker volumes are the preferred and most managed way to persist data in Docker. A Docker volume is created and managed by Docker itself and is stored in Docker’s internal directory on the host system. Docker volumes are independent of containers, meaning they continue to exist even after containers are deleted. 
Docker volumes are portable, safer, and work consistently across different environments.
Path: /var/lib/docker/volumes
Commands:
docker volume ls -- To list all docker volumes on the host machine
docker volume create <volume-name> --> To create a Docker Volume
docker volume rm <volume-name> --> To remove a Docker Volume
docker run -v <docker-volume-name>:<container-path> <image> --> To create container with Docker Volume

2. Bind Mount:
Bind mounts allow you to mount a specific directory or file from the host system directly into a container. Unlike Docker volumes, bind mounts depend heavily on the host’s directory structure and path. 
Any changes made inside the container are immediately reflected on the host, and vice versa. 
Bind mounts are less portable and can cause permission or security issues if not handled carefully.
Commands:
docker run -v <host-path>:<container-path> <image> --> To create a container with Bind Mount

3. Anonymous Volumes:
Anonymous volumes are similar to Docker volumes but do not have a user-defined name. Docker automatically creates them when a container starts, usually when a volume is defined in the Dockerfile without a name.

Docker Networks:
1. Bridge [--network bridge]
The default network driver of Docker is Docker Bridge and the network name is Docker0. By
default, all the containers created without specific network configuration during Docker Run
will be attached to the default network
To access these containers from outside we need to map the ports using publish during
Docker run

2. Host Network [--network host]
Host network will remove any network isolation between the docker host and the containers.
For instance, if you run a container on port 5000, it will be accessible on the same port on the docker host 
without any explicit port mapping. The containers also don’t get their own ip-address.

Host network is generally used for single container nodes as it provides high performance. It
is also used when we have to map large number of ports to the container.

3. Null Network [--network none]
the None network keeps the container in complete isolation, i.e. they are not connected to
any network or container.
One use case might be to run batch jobs which are scheduled programs that are assigned to

Commands:
docker network ls --> To list all the Docker networks on the host machine

docker network rm <network-name> --> To delete a docker network
docker run --network <network-name> <image> --> To create a container attached to a specific network
docker network connect <network-name> <container-name> --> To connect a running container to a network
docker network disconnect <network-name> <container-name> --> To disconnect a running container from a network

Docker Prune:
As we start working with Docker, it’s also easy to accumulate an excessive number of unused
images, containers, and data volumes that clutter the output and consume disk space.
Docker provides a single command that will help to clean up images, containers, volumes, and
networks which are dangling

Commands:
docker system prune --> Removes all dangling images, Unused Networks, Stopped Containers and unused build cache
docker system prune -a --> Removes all unused images, Unused Networks, Stopped Containers and unused build cache
docker image prune --> Removes all dangling images
docker image prune -a --> Removes all Unused images
docker network prune --> Removes all unused networks
docker container prune --> Removes all stopped containers
docker volume prune --> Removes all unused anonymous volumes
docker volume prune -a --> Removes all unused volumes
docker builder prune --> Removes all unused dangling build caches
docker builder prune -a --> Removes all unused build caches

Dangling Images
A dangling image in Docker unused image with no name and tag. It’s leftover when you update or rebuild an image. It just takes up space and can be deleted to free storage.
docker image ls -a --> To list both tagged and dangling images
docker image ls -a -f dangling=true --> To list only dangling images
docker image prune --> To remove Dangling Images

Miscellaneous Commands:

docker ps -aq | xargs docker rm --force --> To remove all containers

Docker Multi Stage Builds:
One of the most challenging things about building images is keeping the image size down. 
The docker multi-stage builds are a way of organizing Dockerfile to minimize the size of the 
final docker image, container and ultimately improve the performance of the container.
In a multi-stage build we will have multiple FROM instructions in a single Dockerfile and each FROM instruction 
begins a new stage. We can selectively copy artifacts from one stage to another.
Basically, instead of keeping all the unnecessary supported libraries, dependency files etc. 
using multi-stage builds we can discord all these components to make our application light and less vulnerable.

Docker Compose:
Docker Compose is used to run multiple containers as a single service. With Docker compose
file we can start all the required containers as a service without the need to start each one of
them separately.

Commands:

docker compose -f <file-name> up --> To use a specific file
docker compose up -d --> To start services in background
docker compose down --> To bring down the services
docker compose ps --> To list the running containers managed by docker compose
